# PII Redaction

Detecting personal information in prompts before it reaches the LLM provider.

> Hi, I'm `[FIRST_NAME]` – reach me at `[PHONE_NUMBER]` or `[EMAIL]`

DTI 6302 – Machine Learning Operations · Fall 2026 · Prof. Mohammad Al Ridhawi
Andrei Sburlan · Jean-Gabriel de Montigny

## Problem statement

As an LLM inference provider, we receive prompts that may include personally identifiable
information (PII): e-mail addresses, phone numbers, social insurance numbers, home addresses and
more. Ingesting this data exposes the provider to additional **security**, **compliance** and
**governance** risks.

```text
Hi, I'm Joseph Zarecki. Text me at 727-360-0442 or email josephzarecki55@yahoo.com
```

**ML task:** given the raw text of a prompt, predict the span(s) of text that contain PII, plus a
classification of each span's PII type. The unit of prediction is a single prompt (document).

## Deployment pattern: redact on the user's device

A machine learning model detects PII inside the LLM chat web app, so it is redacted before the
request is sent.

1. **Write prompt** – the user types in the LLM chat web app.
2. **Detect PII** – the model runs locally in the browser.
3. **Redact** – spans are replaced with typed placeholders.
4. **Send** – the provider receives no PII.

**Monitoring:** the app sends back occasional reports on latency and errors, never sensitive data
or prompt text.

| Input prompt | Redacted prompt sent to the provider |
| --- | --- |
| I purchased a new television from your store on 2023-09-15. My name is Joseph Zarecki. I can be reached at 727-360-0442 or via email at josephzarecki55@yahoo.com. | I purchased a new television from your store on `[DATE]`. My name is `[FIRST_NAME]` `[LAST_NAME]`. I can be reached at `[PHONE_NUMBER]` or via email at `[EMAIL]`. |
| The user name is daxaben_coder. The password is G9t$fR2mXk5. The VPN server address is 12.34.56.78. | The user name is `[USER_NAME]`. The password is `[PASSWORD]`. The VPN server address is `[IPV4]`. |

Typed placeholders keep context for the LLM. PII is not only names and phone numbers: credentials
and IP addresses are labelled too.

## Dataset: NVIDIA Nemotron-PII

| | |
| --- | --- |
| Records | 200,000 synthetic records: 100k train + 100k test (50k personas × `us`/`intl` per split) |
| Entity types | 55+ PII/PHI types (names, SSNs, MRNs, addresses, phones, emails, account numbers, …) |
| Domains | 30 industry domains (the card says 50+) |
| Locales | U.S. and international (international includes ~12% U.S.-style overlap) |
| Formats | Structured (forms, invoices) and unstructured (emails, notes, free text) |
| Labels | Span-level, generated by NVIDIA, so no real personal data is used |
| Licence | CC BY 4.0 |
| Source | <https://huggingface.co/datasets/nvidia/Nemotron-PII> |

**What the data actually contains** (revision `b70ffaf`, pinned in `configs/default.yaml`):

- The card says 50k train / 50k test, but each split has **100,000 rows**: 50,000 `uid`s, each
  generated twice – once with `locale=us` and once with `locale=intl` – sharing the same persona
  attributes (e.g. the same date of birth). This matters for splitting (below). After
  preprocessing, 25 `uid`s are left with a single variant (the other was dropped, see below).
- 30 domains (not 50+), ~1,450 document types, 55 entity labels, ~8.3 spans per document,
  median text length ~770 characters (max ~14.6k). No missing values.
- `spans` is stored as a Python-literal string (single quotes), not JSON.
- **Class imbalance:** the most common label (`company_name`, 10.4% of train spans) is ~36× more
  frequent than the rarest (`sexuality`, 0.29%). Every label still has ≥ 2,300 training spans
  (validation enforces ≥ 1,000), but this is why recall is reported per label and why type F1 is
  macro-averaged. Full counts: `reports/validation/raw_validation.md`.
- The official test split has a noticeably different label mix from train (e.g. `first_name`
  7% → 10% of spans, `company_name` 10% → 6%; Jensen-Shannon distance 0.12).

### Anatomy of one record

```text
Maria, born on 2002-03-05, is a Spanish individual with B+ blood type. Her phone number is 707-859-9753.
```

- `domain`: Identity Verification Services
- `document_type`: Emergency Contact Form
- `document_format`: unstructured
- `locale`: us

| start | end | text | label |
| ---: | ---: | --- | --- |
| 0 | 5 | Maria | first_name |
| 15 | 25 | 2002-03-05 | date_of_birth |
| 32 | 39 | spanish | race_ethnicity |
| 56 | 58 | B+ | blood_type |
| 91 | 103 | 707-859-9753 | phone_number |

Note: the span text `spanish` is lowercase while the source text says `Spanish`. Validation
found this in 0.8% of spans; 0.7% of span texts are also stored as integers. Character offsets are
treated as the source of truth and the span `text` field is dropped.

### Split strategy

The unit of prediction is a document, but documents are **grouped by `uid`**: the `us` and `intl`
variants of a persona share PII values, so a random row split would leak near-duplicates between
train and validation.

| Split | Source | Docs | uids |
| --- | --- | ---: | ---: |
| train | HF `train`, uids not hashed into validation | 90,070 | 45,041 |
| validation | HF `train`, `sha256(seed:uid) mod 10000 < 1000` (10% of uids) | 9,915 | 4,959 |
| test | HF `test` minus 10 docs with overlapping spans (held out until final model selection) | 99,990 | 50,000 |

- Hash-based assignment is deterministic, independent of row order, and keeps both locale variants
  of a persona in the same split.
- Any train/validation row whose `uid` or exact text also appears in test is removed (currently
  none), and the processed-data validation asserts zero `uid` and text overlap between every pair
  of splits.
- Model selection uses validation only; test is touched once for the final model.
- **Residual risk – PII value reuse:** the generator reuses specific values across personas. A
  review found ~14% of validation documents share at least one value (an address, password, user
  name, phone or card number) with a training document of a *different* `uid`. This cannot inflate
  the regex baseline, but a learned model could memorise values. Checkpoint 3 will add a recall
  slice over entities whose value never appears in train.

### Data validation

Validation runs as a pipeline step **before** any training, on the raw data and again on the
processed splits. Errors stop the pipeline; warnings are recorded. Each run writes
`reports/validation/{raw,processed}_validation.{json,md}` (checks, observed values, thresholds,
split summaries, label distributions and examples of issues).

| Kind | Rules (thresholds in `configs/default.yaml` → `validation`) |
| --- | --- |
| Schema / types | Required columns present, string dtypes, `spans` parses to a list of `{start, end, text, label}` with integer offsets |
| Missing values | No nulls, no blank strings |
| Domain | `locale ∈ {us, intl}`, `document_format ∈ {structured, unstructured}`, labels in the known 55-label set, `0 ≤ start < end ≤ len(text)`, span text equals `text[start:end]` up to letter case, ≤ 2 records per `uid` |
| Statistical | Text length in [20, 20000] chars; case-mismatch span rate ≤ 2%; docs with overlapping spans ≤ 0.2%; docs with no spans ≤ 0.1%; duplicate texts ≤ 0.1%; ≥ 1,000 training spans per label |
| Leakage | Zero `uid` / exact-text overlap between splits |
| Drift (warning) | Label-distribution Jensen-Shannon distance between splits ≤ 0.1 (train vs test is 0.12, see above) |

Preprocessing then makes the data strictly clean: canonical sorted `{start, end, label}` spans,
documents with overlapping spans dropped (24 of 200k), exact duplicate texts dropped (1).

Custom validation is used rather than TFDV/Great Expectations because most rules are about nested
span structure relative to the text, which those tools don't express naturally.

## Success metrics

| Metric | Role | Definition |
| --- | --- | --- |
| Detection recall | **Primary** | Share of PII entities that get redacted, regardless of type, reported per entity type. Every miss means the provider receives PII. |
| Detection precision | | Share of redacted text that is actually PII. Low precision means over-redaction and lost context. |
| Type classification (macro-F1) | Secondary | Among correctly detected entities only: F1 per label over labels that occur among detected entities, macro-averaged. Missed entities are not counted again here. A wrong type is still redacted: it affects context, not privacy. |
| Latency (p95) | Operational | Time to redact a prompt in the browser on a low-end target device; must not noticeably delay sending. |

Detection recall counts a gold entity as redacted when **all** of its characters are covered by
predicted spans of any type (`evaluation.min_coverage`). Precision is measured on characters.
Metrics are also sliced by `locale`, `document_format` and `domain`.

Numeric targets are still to be agreed by the team, informed by the baseline results below.

## Baselines

1. **Rules-based system** – regular expressions for structured formats (e-mail addresses, phone
   numbers, SIN/SSN, postal codes), e.g. `phone: \b\d{3}-\d{3}-\d{4}\b`. Strong on fixed formats;
   cannot reliably catch names, street addresses or free-text details.
2. **Small model** – trained on a subset of the training data before scaling up to the full
   dataset. Shows how much learning adds over hand-written rules, at low training cost.

Both baselines are scored with the same metrics as the main TensorFlow/Keras model.

### Regex baseline results (validation split, 9,915 docs, 81,770 entities)

| Metric | Value |
| --- | ---: |
| Detection recall | **0.329** |
| Character precision | 0.993 |
| Character recall | 0.465 |
| Type macro-F1 (detected entities) | 0.378 |
| Type accuracy (detected entities) | 0.898 |

Per label, the rules behave as expected: near-perfect recall on fixed formats (MAC 1.00, SSN 1.00,
IPv4 1.00, email 0.99, card 0.98, IPv6 0.97, URL 0.95, dates 0.87, phone 0.83) and **zero** on
names, companies, street addresses, cities, occupations and other free-text attributes – which are
most of the entities. Slices by locale (us 0.32 / intl 0.34) and document format are flat. The full
per-label and per-slice tables are in `reports/baseline/regex_baseline_validation.md` (plus
`_per_label.csv` and a `.json` summary with the MLflow run id and git commit), and are also logged to
MLflow.

## Risks

| Risk | Description |
| --- | --- |
| Synthetic data | May not reflect real-world prompts, particularly LLM chat logs. |
| Text only | File uploads (PDFs, documents, spreadsheets) would need OCR or text extraction first, if in scope. |
| Under-redaction | Missed PII is retained by the LLM provider. |
| Over-redaction | Users lose meaningful context, which may lead to customer churn. |
| Locale gaps | Canadian PII such as SINs and postal codes may be underrepresented. |
| Encoding | Character positions can differ between Python (training) and JavaScript/TypeScript (browser). |

## Pipeline & orchestration

```text
ingest ─▶ validate_raw ─▶ preprocess ─▶ validate_processed ─▶ evaluate_baseline ─▶ (train, checkpoint 3)
```

Every step is a plain function in `pipelines/steps.py` that reads inputs from disk, writes outputs
to disk and returns a small JSON summary. The same functions run two ways:

- **Airflow** (`pipelines/dags/pii_redaction_pipeline.py`) – the orchestrated path. Tasks pass
  only summaries through XCom. `ingest` retries 3× with exponential backoff (network); validation
  tasks never retry, because a failed data check is deterministic and needs a human. The DAG is
  manually triggered and takes a `config` param.
- **CLI** (`uv run python -m pipelines.cli <step…|all>`) – for quick iteration and Docker.

```bash
make data && make baseline     # CLI
make airflow-run               # one DAG run, in-process
make airflow                   # UI: trigger pii_redaction_pipeline from http://localhost:8080
```

Local Airflow state (SQLite metadata DB, logs, generated admin password) lives in `.airflow/`
(git-ignored).

## Training & experiment tracking

Experiments are tracked in **MLflow** (`sqlite:///mlflow.db`, artifacts in `mlartifacts/`, both
git-ignored). Each run records:

- params: model settings, seed, dataset repo/revision, validation fraction
- metrics: `validation.detection_recall`, `char_precision`, `char_recall`, `type_macro_f1`,
  per-label recall (`validation.recall.<label>`) and per-slice recall
- tags: `data_version`, `git_commit`, `git_dirty` (tracked files differ from the commit),
  `airflow_dag_run_id` (when run by Airflow), `model_family`, `eval_split`
- artifacts: full metrics JSON, Markdown report, per-label CSV, processed-data manifest

Before evaluating, the pipeline checks that the processed splits were built from the current raw
files, config and data code (`data_version` matches and file hashes match); otherwise it fails and
asks for `make data`. Evidence runs should be made from a clean commit (`git_dirty=false`).

Keras training runs (checkpoint 3) will log to the same experiment for comparison.

## Limitations & known issues

- The official test split has a shifted label distribution relative to train (JS distance 0.12);
  validation is drawn from train, so test results may be lower than validation results.
- Documents with overlapping spans (24 of 200k) are dropped because the planned tagging scheme
  is flat.
- Span offsets are Python code-point indices; the browser runtime works in UTF-16 code units, so
  offsets must be converted for non-BMP characters (e.g. emoji).
- `make airflow-run` prints a harmless SQLAlchemy `MissingGreenlet` traceback from Airflow's SQLite
  connection cleanup after the run has already succeeded.
